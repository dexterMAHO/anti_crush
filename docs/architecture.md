# معماری و تصمیم‌ها

- Domain: نرمال‌سازی، مجوز نقش‌ها، خطاهای کاربری و قالب متن عمومی؛ بدون وابستگی به تلگرام/ORM.
- Application: ثبت، تصمیم‌گیری، کنترل محدودیت، صف انتشار و تطبیق نتیجه نامشخص.
- Infrastructure: مدل‌ها، Repository، PostgreSQL، gateway تلگرام و adapter AI.
- Presentation: ترجمه فرمان‌ها/دکمه‌ها به عملیات سرویس و پاسخ‌های فارسی.
- main: inbox پایدار، singleton lock و چرخه worker.

مرز تراکنش، هر Use Case است. Repository از Session اختصاصی آن تراکنش استفاده می‌کند.
قفل ردیف کاربر نرخ ارسال را بین تراکنش‌ها هماهنگ می‌کند؛ قفل ردیف پیام
تصمیم‌های رقابتی و انصراف در برابر شروع انتشار را سری می‌کند.
Worker انتشار با SKIP LOCKED پیام را claim می‌کند، تراکنش را commit می‌کند و سپس
Telegram را فراخوانی می‌کند. commit پایگاه داده و ارسال Telegram تراکنش مشترک
ندارند؛ وضعیت UNCERTAIN جایگزین ادعای exactly-once است.
قطع پس از claim حتی قبل از ارسال، برای ایمنی UNCERTAIN محسوب می‌شود.

تمام زمان‌ها UTC هستند. JSON ورودی هر update جدا از موجودیت‌های قابل جست‌وجو نگهداری
می‌شود. هیچ garbage collector یا دستور حذف محتوا وجود ندارد.
محدودیت‌های کاربر، پروفایل و نقش‌ها وضعیت جاری دارند؛ تغییرات مدیریتی در audit و
پروفایل‌های دریافتی در inbox باقی می‌مانند. پذیرش هر نسخه policy نیز audit می‌شود.

MVP از polling استفاده می‌کند و یک process دارد؛ قفل اتصال PostgreSQL تا پایان
عمر process حفظ می‌شود. چند poller برای یک توکن مجاز نیست.
مهاجرت‌ها snapshot مستقل schema هستند، نه import مستقیم مدل‌های در حال تغییر.
