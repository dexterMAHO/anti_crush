 # ربات اعتراف ناشناس

ربات فارسی تلگرام با Python 3.12، aiogram 3، PostgreSQL، SQLAlchemy و Alembic.

## سیاست داده مطابق درخواست پروژه

ناشناس‌بودن فقط در کانال است. متن اصلی و نرمال‌شده، ارتباط هویت و پیام، پروفایل
دریافتی، JSON تمام Updateهای تحویل‌شده به ربات، نتایج پالایش، پذیرش قوانین، تصمیم‌ها،
محدودیت‌ها و تلاش‌های انتشار بدون حذف خودکار ذخیره می‌شوند. انصراف به معنی توقف
انتشار است، نه حذف اطلاعات. این سیاست قبل از پذیرش به کاربر نشان داده می‌شود.
دسترسی هویت در رابط مدیریت فقط برای مالک است و Audit می‌شود؛ مدیر دیتابیس نیز
طبیعتاً به اطلاعات دسترسی دارد. نسخه مستند اصلی در docs/requirements.md است؛
سیاست نگهداری این README جایگزین پیشنهاد حذف ۳۰/۹۰روزه آن شده است.

«همه اطلاعات» یعنی اطلاعاتی که Bot API به ربات تحویل می‌دهد؛ شماره تلفن،
IP، پیام‌های خارج از دسترس ربات و فایل اصلی رسانه‌ها خودکار در دسترس نیستند.
برای رسانه‌های دریافتی JSON و file_id ذخیره می‌شود؛ دانلود باینری رسانه خارج از MVP است.
این سامانه فقط پیام متنی را برای انتشار می‌پذیرد.

## اجرا با Docker

1. فایل نمونه را کپی کنید: `cp .env.example .env`
2. BOT_TOKEN، CHANNEL_ID عددی، OWNER_TELEGRAM_ID و رمز دیتابیس را تنظیم کنید.
   رمز داخل DATABASE_URL باید با POSTGRES_PASSWORD هماهنگ و URL-encoded باشد.
3. ربات را مدیر کانال کنید و مجوز ارسال پیام بدهید.
4. اجرا: `docker compose up -d --build`
5. بررسی: `docker compose ps` و `docker compose logs --tail=100 bot`

برای استقرار یک شاخه یا کامیت مشخص روی سرور:
`./scripts/deploy.sh feat/button-ui` (بدون آرگومان همین شاخه پیش‌فرض است).
اسکریپت وجود `.env` و پاک بودن Working tree را بررسی می‌کند، شاخه را از `origin`
می‌گیرد، سرویس را build و اجرا می‌کند و تا Healthy شدن ربات صبر می‌کند؛ در صورت
ناموفق بودن، لاگ را چاپ و کد را به کامیت قبلی برمی‌گرداند. Rollback فقط کد را
برمی‌گرداند و Migrationهای اعمال‌شده را بازنمی‌گرداند؛ پیش از استقرار Backup بگیرید.
مخزن پس از اجرا در حالت detached HEAD است؛ برای بازگشت `git checkout main` بزنید.

Migration پیش از اجرای ربات اعمال می‌شود. دیتابیس در Volume پایدار است و هیچ
پورت عمومی ندارد. از `docker compose down -v` استفاده نکنید مگر قصد حذف داده دارید.
توکن واقعی در مخزن قرار ندهید. برای فعال‌شدن واقعی ربات نیاز به توکن و کانال دارید.

## توسعه و تست

```sh
uv sync --frozen
uv run pytest
uv run ruff check .
uv run ruff format --check .
# DATABASE_URL از .env یا محیط خوانده می‌شود:
uv run alembic upgrade head
uv run python -m confession_bot.main
```

برای تست PostgreSQL، یک دیتابیس **مجزای تست** بسازید و TEST_DATABASE_URL را تنظیم کنید.
Fixture تست جدول‌های دیتابیس تست را پاک و دوباره ایجاد می‌کند؛ هرگز آدرس Production ندهید.
تست پیش‌فرض SQLite است؛ برای بررسی قفل و هم‌زمانی حتماً PostgreSQL لازم است.

## رابط دکمه‌ای و استاندارد آن

رابط اصلی، دکمه‌ای و داینامیک است؛ تعریف دکمه‌ها در
`src/confession_bot/presentation/ui.py` متمرکز شده و استاندارد زیر را دنبال می‌کند:

- منوی پایین صفحه (Reply Keyboard) تنها مسیر ناوبری است و برای هر کاربر از نقش
  او در دیتابیس ساخته می‌شود؛ دکمه «صف بررسی» فقط به مدیران نشان داده می‌شود.
- دکمه‌های شیشه‌ای (Inline) فقط عملیات مربوط به یک پیام مشخص و جابه‌جایی صفحه‌ها
  را حمل می‌کنند؛ هر دکمه به مجوز متناظر خود گره خورده و هنگام فشردن، نقش دوباره
  از دیتابیس خوانده و بررسی می‌شود. پنهان‌بودن دکمه جای مجوز را نمی‌گیرد.
- قالب `callback_data` همیشه `action` یا `action:argument` است و بسیار کوتاه‌تر
  از محدودیت ۶۴ بایت تلگرام می‌ماند.
- عملیات غیرقابل‌بازگشت (رد پیام و انصراف از انتشار) دو مرحله‌ای است؛ تأیید با
  پسوند `!` در همان action فرستاده می‌شود.
- به هر فشردن دکمه پاسخ داده می‌شود تا کلاینت در حالت انتظار نماند.
- برچسب‌ها متن فارسی ساده و بدون ایموجی هستند. برچسب‌های منو مانند دستور رفتار
  می‌کنند و هرگز به‌عنوان متن پیام ثبت نمی‌شوند.
- تمام دستورهای متنی قبلی دست‌نخورده باقی مانده‌اند و معادل دکمه‌ها هستند.

کاربر در «پیام‌های من» برای هر پیام وضعیت بررسی و انتشار و دکمه انصراف را می‌بیند.
مدیر در «صف بررسی» برای هر پیام کد پیگیری، سطح خطر، وضعیت‌ها و متن کامل پیام را
همراه دکمه‌های تأیید، رد، بررسی ویژه، نیازمند اصلاح، ثبت در صف انتشار، مشاهده
فرستنده و تاریخچه می‌بیند. دکمه «مشاهده فرستنده» متن پیام را در کنار شناسه عددی،
نام و نام کاربری فرستنده نشان می‌دهد؛ این دکمه مانند `/identity` فقط برای مالک
کار می‌کند، دلیل «تصمیم مدیر از طریق دکمه» را ثبت می‌کند و در Audit ذخیره می‌شود.
تصمیم‌های دکمه‌ای هم همین دلیل ثابت را ثبت می‌کنند؛ برای دلیل اختصاصی باید از
دستور متنی استفاده شود.

## دستورات

`/start`، `/rules`، `/accept`، `/help`، `/mine`، `/withdraw CODE`

مدیریت:
- `/queue PAGE`: شماره صفحه اختیاری؛ ده پیام قدیمی آماده بررسی/انتشار با دکمه‌ها.
- `/approve CODE دلیل`، `/reject CODE دلیل`، `/escalate CODE دلیل`،
  `/needs_edit CODE دلیل`.
- `/publish CODE`: صف انتشار؛ تأیید به‌تنهایی باعث انتشار نمی‌شود.
- `/identity CODE دلیل`: هویت، پروفایل و متن پیام با ثبت دلیل.
- `/restrict CODE HOURS دلیل`: صفر دائمی، منفی یک رفع، عدد مثبت ساعت.
- `/role TELEGRAM_ID ROLE`: SENIOR_ADMIN، MODERATOR، PUBLISHER، یا NONE.
- `/history CODE`: تاریخچه بدون شناسه مدیران یا داده هویتی.
- `/reconcile CODE MESSAGE_ID دلیل`: مالک پس از بررسی کانال، نتیجه نامشخص را
  با شناسه واقعی پیام تطبیق می‌دهد؛ صفر یعنی عدم انتشار قطعی و امکان تلاش محدود مجدد.

OWNER همه مجوزها را دارد. SENIOR_ADMIN بررسی حساس و محدودسازی؛ MODERATOR بررسی
عادی؛ PUBLISHER انتشار تأییدشده. نقش در هر عملیات از دیتابیس خوانده می‌شود.
فقط مالک اولیه از Environment ایجاد می‌شود و قابل تنزل در رابط ربات نیست.

## انتشار و پایداری

Long polling با صندوق ورودی پایدار اجرا می‌شود. Update قبل از پردازش ثبت می‌شود.
یک قفل advisory در PostgreSQL از اجرای هم‌زمان دو نمونه جلوگیری می‌کند.
Worker پیام‌های دریافت‌شده را پالایش می‌کند. قواعد پایه فارسی و Finglish کامل نیستند؛
تمام پیام‌ها بررسی انسانی دارند. پیام حساس یا خطای AI به بررسی ویژه می‌رود.

انتشار ابتدا با یک operation ID در دیتابیس ثبت و سپس از طریق sendMessage انجام
می‌شود؛ هویت فرستنده forward نمی‌شود. Timeout یا قطع هنگام ارسال به UNCERTAIN
می‌رود و خودکار تکرار نمی‌شود. خطای قطعی حداکثر سه بار تلاش می‌شود.
پس از Crash، عملیات PUBLISHING نامشخص محسوب می‌شود.
اعلان کاربر از انتشار مستقل است و شکست آن انتشار را تکرار نمی‌کند.
تحویل اعلان‌ها at-least-once است؛ قطع درست بعد از ارسال می‌تواند اعلان تکراری ایجاد کند.
پاسخ فرمان‌ها نیز ممکن است پس از Crash تکرار شود؛ انتشار کانال از این مسیر جداست.

## AI اختیاری

AI_MODERATION_ENABLED=true و AI_URL، AI_API_KEY و AI_MODEL را تنظیم کنید.
Adapter یک endpoint HTTPS مستقل از فروشنده می‌خواهد؛ مستقیماً endpoint چت OpenAI نیست.
درخواست: `{"text":"متن با الگوهای حساس پوشانده‌شده","model":"..."}`
پاسخ:
```json
{"categories":["HARASSMENT"],"risk_level":"HIGH","reason":"توضیح",
 "requires_human_review":true}
```
خروجی با Pydantic بررسی می‌شود. هیچ دستور داخل متن کاربر به عملیات اجرایی تبدیل
نمی‌شود. Timeout برابر ۱۵ ثانیه است. خروجی AI مجوز انتشار نمی‌دهد.
با تغییر شرایط ارسال داده به سرویس خارجی، POLICY_VERSION را تغییر دهید تا پذیرش
دوباره لازم شود. نگهداری داده نزد Provider خارجی تابع تنظیمات همان سرویس است.

## پشتیبان و بازیابی

ابزار age را روی میزبان و کلید خصوصی را خارج از سرور ربات نگهداری کنید.
`BACKUP_RECIPIENT=age1... ./scripts/backup.sh`
اسکریپت pg_dump را مستقیماً رمزگذاری می‌کند؛ فایل خام روی دیسک نوشته نمی‌شود.
آن را با cron روزانه اجرا و نسخه رمزگذاری‌شده را به محل مستقل منتقل کنید.
حذف خودکار Backup فعال نیست؛ پایش ظرفیت ذخیره‌سازی بر عهده ارائه‌دهنده است.

بازیابی را ابتدا در دیتابیس خالی جدا انجام دهید:
`AGE_IDENTITY=/secure/key.txt RESTORE_DATABASE_URL=postgresql://... ./scripts/restore.sh backups/FILE.dump.age`
پس از بررسی شمارش کاربران، پیام‌ها، audit و migration، سرویس را به دیتابیس بازیابی‌شده
متصل کنید. پیام‌های در حال انتشار را قبل از ارسال مجدد در کانال بررسی کنید.

## مرزهای نسخه

Webhook، پنل وب، ویرایش متن ارسالی، حذف/ویرایش پست کانال و رسانه خارج از این نسخه‌اند.
NEEDS_EDIT درخواست ارسال نسخه جدید است؛ پیام قبلی حفظ می‌شود.
از اتصال مستقیم به کانال واقعی در تست‌ها استفاده نمی‌شود.
پیش از راه‌اندازی عمومی باید smoke test با ربات/کانال آزمایشی و تمرین بازیابی انجام شود.

مراجع فنی: [aiogram Dispatcher](https://docs.aiogram.dev/en/latest/dispatcher/dispatcher.html)
و [SQLAlchemy Sessions](https://docs.sqlalchemy.org/en/20/orm/session_api.html).

## وابستگی‌ها

به علت عدم دسترسی مستقیم این محیط به PyPI، registry پیش‌فرض در pyproject.toml
روی mirror Aliyun تنظیم شده است. uv.lock نسخه و hash بسته‌ها را ثبت می‌کند.
برای تغییر registry به PyPI، URL تنظیم tool.uv.index را تغییر دهید و uv lock را اجرا کنید.

## پیدا کردن شناسه کانال و مالک

برای راه‌اندازی اولیه، بدون نیاز به دیتابیس یا تنظیم کامل .env:

```sh
uv sync --frozen
# اگر ربات اصلی در حال اجراست:
docker compose stop bot
uv run --frozen python scripts/find_telegram_ids.py
```

توکن از BOT_TOKEN محیط یا فایل .env خوانده می‌شود؛ اگر موجود نباشد، پنهان پرسیده
می‌شود. اسکریپت دو متن یک‌بارمصرف متفاوت نمایش می‌دهد: متن مالک را از حساب شخصی
خود به ربات بفرستید؛ متن کانال را بعد از ادمین‌کردن ربات در کانال منتشر کنید.
شناسه‌ها به شکل آماده کپی در .env نمایش داده می‌شوند. فایل .env خودکار تغییر نمی‌کند.

مهلت پیش‌فرض پنج دقیقه است؛ با `--timeout 600` می‌توان آن را افزایش داد.
فایل تنظیمات دیگر با `--env-file /path/to/.env` قابل انتخاب است.
اسکریپت Webhook موجود را حذف نمی‌کند و نباید هم‌زمان با poller اصلی اجرا شود.

Updateهای خوانده‌شده قبل از جلو بردن offset، در `.local/id-discovery.jsonl`
با مجوز ۶۰۰ ذخیره می‌شوند. این فایل در Git و Docker image وارد نمی‌شود.
این ابزار مخصوص راه‌اندازی است؛ پیام‌هایی که طی آن دریافت می‌شوند خودکار وارد
صف بررسی برنامه اصلی نمی‌شوند. برای ربات فعال، در زمان توقف پذیرش پیام اجرا کنید.

مرجع: [Telegram getUpdates](https://core.telegram.org/bots/api#getupdates).

اگر ابزار شناسایی خطای ۴۰۴ یا توکن نامعتبر داد، توکن را مستقیم و پنهان وارد کنید:
`python scripts/find_telegram_ids.py --prompt-token`
این گزینه BOT_TOKEN محیط و .env را نادیده می‌گیرد. ابزار منبع توکن را نشان می‌دهد،
اما مقدار آن را چاپ نمی‌کند. توکن باید متعلق به BotFather باشد، بدون پیشوند bot
یا آدرس API. متغیر محیطی BOT_TOKEN در حالت عادی بر مقدار فایل .env اولویت دارد.
